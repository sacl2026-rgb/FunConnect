## 2. What We Can Replicate (esptool Small-to-Small)

After one mBlock upload initializes the device:

1. Read sector 0x558000 via esptool (stub flasher, 115200 baud)
2. Find code_start (first "from cyberpi" after header)
3. Find code_end (position of 0x08 terminator byte)
4. Replace bytes [code_start:code_end] with new program code
5. Space-pad (0x20) if new code is shorter than old code
6. Write sector back
7. Touch nothing else - preserve checksum, terminator, metadata

**Confirmed:** Blue, green, red - multiple color cycles on C2.

## 3. What We Discovered

### 3.1 Two Program Formats

Small programs have header + code + checksum + 0x08 + metadata.
Large programs fill the entire sector with code, no markers.
mBlock handles both; we can only write small over small.

### 3.2 Halocode Protocol Over Serial

f3/f4 framing at 115200 baud over CH340. TYPE_SCRIPT (0x28) sends
Python expressions. CyberPiOS responds with JSON.

### 3.3 CyberPiOS Internal API

Accessible via Halocode: config, NVS, communication protocol groups.
upload_broadcast exists but does not persist program to flash.

### 3.4 Official Makeblock Library

makeblock v0.1.8 contains HalocodePackData with full frame construction.
All TYPE/MODE constants and protocol group IDs documented.

### 3.5 BLE Transport

Same f3/f4 protocol over BLE characteristics 0xffe3 (write) / 0xffe2 (notify).

## 4. What We Have Not Yet Solved

### 4.1 mBlock Upload Mechanism

mBlock upload routes through CyberPiOS internally. We see the RESULT
(bytes on flash) but not the MECHANISM. All 256 TYPE bytes and MODE
values tested via BLE and serial - none trigger upload persistence.

### 4.2 Factory-Fresh Initialization

Devices that have never seen mBlock reject all esptool writes.
mBlock transitions them out of this state. We cannot replicate.

### 4.3 Format Transitions

Small-to-large, large-to-small, default-to-any: mBlock does them all.
Our esptool only works small-to-small. NVS run_script_type alone
is insufficient - CyberPiOS must also reformat the sector internally.

### 4.4 Checksum Algorithm

2-byte checksum at 0xCF-0xD0 generated by CyberPiOS. CRC16, XOR,
Fletcher, additive - all failed. Appears to include code content
and device-specific data.

### 4.5 Binary Metadata Format

Bytes at 0xD2+ generated per-device. Cannot clone between devices
(different MACs). Cannot omit. Format unknown.

### 4.6 Persistent State Flag

mBlock sets a flag enabling future esptool writes. Survives format
changes and reboots. Cleared by factory reset. Location not found
(ruled out: NVS, factory, otadata, FAT, EFUSE).

### 4.7 Web Serial Browser Path

esptool-js CDN had import conflicts and writeFlash hangs.
CLI esptool is reliable. Browser path not yet stabilized.

---

## 5. Key Lessons

1. Read first, never build from scratch
2. Space-pad (0x20), never zero-pad (0x00)
3. Preserve all bytes outside the code region
4. New code must fit in old code's space
5. Use stub flasher at 115200 baud
6. mBlock routes through CyberPiOS internal flash writer
7. All transitions ARE possible - mBlock proves it
